Formal methods for exploit/patch validation & build provenance\n\n**Sanitizers as ground-truth oracle (the workhorse).** ASAN (use-after-free, heap/stack overflow, use-after-return/scope, leaks) and UBSAN (integer overflow, bad shifts, misaligned/undefined behavior) provide a *deterministic verdict*. The formalization now used as a research/competition standard: **\"accept a PoC only when it triggers the expected sanitizer report, and validate a patch only when that report disappears\"** — \"aligning with DARPA AIxCC's methodology which uses sanitizers as the ground truth for vulnerability discovery and repair.\" (SEC-bench, arXiv 2506.11791.) https://arxiv.org/pdf/2506.11791\n\n**Patch-neutrality / non-regression gate.** A patch is valid only if: (1) the PoC no longer triggers the sanitizer AND (2) functional tests still pass. AIxCC challenges ship OSS-Fuzz-compatible harnesses *and* functional test suites precisely so patches can be checked for both security fix and behavior preservation (Buttercup docs). This is lightweight *equivalence checking by test-suite*; heavier equivalence checking (proving the patched function equivalent except on the exploiting input) is the formal frontier — see \"A Systematic Study of LLM-Based Architectures for Automated Patching\" (2603.01257) and PatchIsland (2601.17471).\n\n**Verified reasoning / formal-methods-as-checker:** Lean/Coq-backed pipelines are emerging — \"Agentic Verification of Software Systems\" (2511.17330), \"Towards Verified Code Reasoning by LLMs\" (2509.26546), VeriBench.\n\n**Build/evidence provenance — in-toto / SLSA / Sigstore:** The plumbing that makes a certificate *trustworthy to a third party*:\n- **in-toto Attestation Framework (ITE-6)** defines the common **DSSE envelope** that carries provenance claims (builder identity, source commit, build params, materials).\n- **Sigstore keyless signing:** CI authenticates via OIDC → **Fulcio** issues a short-lived cert → **cosign** signs the artifact/attestation → the event is logged in **Rekor** (append-only transparency log). Verifiers check signature + cert chain + OIDC claims + Rekor inclusion.\n- GitHub **artifact attestations** now make SLSA L2 achievable out-of-the-box. Research: \"Kettle: Attested builds for verifiable software provenance\" (2605.08363).\n- https://secure-pipelines.com/ci-cd-security/artifact-provenance-attestations-slsa-in-toto/ and https://www.infoq.com/news/2025/08/provenance/\n\n**Maturity:** Sanitizer oracle = **production/standard**. in-toto/SLSA/Sigstore = **production**. Formal patch-equivalence = **research**.\n\n**Pipeline fit:** Sanitizer verdict = the confirm signal for memory bugs; test-suite pass = the \"didn't break function\" signal; DSSE/Sigstore = the signature layer of your certificate (§7).\n\n---\n\n## 5. Anti-hallucination for agents (what actually works)\n\n**The single most important empirical fact — the generator-verifier gap:** for a large class of problems, *checking* a solution is far easier and more reliable than *producing* one. Your architecture exploits this: never trust generation, always route through a (ideally deterministic) verifier.\n\n**Techniques ranked by how much they actually help, strongest first:**\n1. **Deterministic tool-grounded verification / \"only the checker mints truth.\"** The strongest new result is **EG-VAR — \"Evidence-Grounded Verified Agentic Reasoning\"** (arXiv 2607.12650): a Lean-4 tool-calling architecture where **the Lean kernel is the sole minter of \"Verified\" claims** via tool-attestation axioms; \"every verified output structurally descends from an attested tool call and a kernel-checked chain of valid inference; residual outputs are **honest Abstain with a replayable audit trail**.\" Results: **120/120** vs a 95% same-tool baseline; **100% source-faithful** under counterfactual stress vs 80–90% for same-tool, 50–80% no-tool. This is your exact philosophy formalized: *the LLM can propose but cannot assert; unproven ⇒ Abstain.* https://arxiv.org/abs/2607.12650v1 . Companion: \"Tool Receipts, Not Zero-Knowledge Proofs: Practical Hallucination Detection for AI Agents\" (2603.10060).\n2. **Verifier models / generative verifiers (when no deterministic oracle exists).** \"Generative Verifiers: Reward Modeling as Next-Token Prediction\" (GenRM, arXiv 2408.15240) — trained verifiers beat off-the-shelf LLM judges. \"Multi-Agent Verification: Scaling Test-Time Compute with Multiple Verifiers\" (2502.20379). CompassVerifier (2508.03686). Caveat directly relevant to security: verifiers \"without integration with symbolic solvers or external tools are prone to hallucinations\" — so verifier LLMs are a *ranker/triager*, not the final oracle.\n3. **Adversarial stage-gated review — refute the finding before promoting it.** \"Refute-or-Promote: An Adversarial Stage-Gated Multi-Agent Review Methodology for High-Precision LLM-Assisted Defect Discovery\" (2604.19049). Pair with the industrial FP-filtering results: \"Reducing False Positives in Static Bug Detection with LLMs\" drove FP from **>98% to 6.3%** (2601.18844); \"Sifting the Noise\" (2601.22952); MultiVer (2602.17875).\n4. **Self-consistency** (sample N, keep only stable claims) — moderate, costs 2–3×; MARCH multi-agent self-check (2603.24579); AGSER attention-guided self-reflection. Useful as a *pre-filter*, not proof.\n\n**Maturity:** Deterministic tool-grounding = **the winning pattern** (AIxCC, Big Sleep, EG-VAR). Verifier models = **strong research→production**. Self-consistency = **commodity**.\n\n**Pipeline fit:** Structure the whole system as EG-VAR does: findings carry an epistemic status of `{Verified | Abstain}`; only the oracle transitions to `Verified`; everything else is an explicit abstention with an audit trail. Use verifier LLMs + refute-or-promote only to *rank and cull* proposals cheaply before the oracle.\n\n---\n\n## 6. Confidence calibration / Bayesian belief over findings\n\n**The technique.** Attach a *calibrated* probability (or a distribution-free coverage guarantee) to each finding, and score the strongest **benign alternative** explicitly so you're doing likelihood-ratio reasoning, not confirmation.\n\n**Conformal prediction — the rigorous route to abstention with guarantees:**\n- **ConU — \"Conformal Uncertainty in LLMs with Correctness Coverage Guarantees\"** (2407.00499): distribution-free finite-sample coverage over LLM outputs.\n- **Conformal Abstention** gives two finite-sample guarantees you want: a **participation guarantee** (bound on how often the system answers) and a **conditional correctness guarantee** (bound on error *given* it answered). This is precisely the knob for \"only emit a finding when we can bound its false-positive rate.\"\n- **PASC — Pipeline-Aware Conformal Prediction with Joint Coverage Guarantees for Multi-Stage LLM Pipelines** (2605.18812) — directly relevant because your propose→verify→certify flow is multi-stage.\n- Learning Conformal Abstention Policies (RL + CP, adaptive thresholds); Differentiable Conformal Training for LLM Reasoning Factuality (2604.20098); Selective Conformal Risk Control (2512.12844).\n\n**Competing-hypothesis / benign-alternative scoring:**\n- **Bayesian Analysis of Competing Hypotheses (BACH)** and **ACH structured with Bayesian networks** (ScienceDirect S2193943821000194) — intelligence-community method for finding the hypothesis \"least inconsistent with the evidence,\" giving a probabilistic characterization of competing hypotheses. Adapt as: for each candidate, enumerate `{real-vuln, benign-behavior, environment-artifact, coincidence}` and require the evidence to shift the posterior toward `real-vuln` past a threshold — which the deterministic oracle then makes moot when it fires.\n\n**Maturity:** Conformal prediction is **mathematically mature**; its application to security decisions is **early research**. Bayesian ACH is **mature in intel analysis**, novel in AI security tooling.\n\n**Pipeline fit:** Two layers. (a) *Pre-oracle*: conformal calibration on a labeled corpus lets the proposer **abstain** on low-confidence candidates with a provable coverage guarantee (controls cost + FP rate before you pay for oracle runs). (b) *For irreducibly-statistical oracles* (blind/timing, §Diff-4), conformal/SPRT gives the confirmation threshold itself a guarantee.\n\n---\n\n## 7. Reproducible / re-runnable evidence (the \"certificate\")\n\n**The technique.** A finding becomes a self-contained artifact any third party can re-execute offline to watch the oracle fire — no trust in your LLM required. This is the \"proof-carrying\" endgame.\n\n**The proven model — OSS-Fuzz / ClusterFuzz reproducer:** every issue carries a **testcase file** (exact bytes fed to the target), automatically **minimized**, plus the fuzzer artifact and build, labeled **\"Reproducible\"** when it reliably re-triggers. Anyone downloads the testcase + builds the target + runs → same sanitizer crash. https://google.github.io/oss-fuzz/advanced-topics/reproducing/ and https://chromium.googlesource.com/chromium/src/+/HEAD/docs/security/clusterfuzz-for-shepherds.md\n\n**The CGC model:** the PoV is a *compiled binary* the framework re-runs against a fresh randomized challenge — reproducibility + generalization in one artifact.\n\n**How to assemble your certificate (concrete spec):** a signed bundle containing:\n1. **Target pin:** container/image **digest** (immutable) + exact toolchain + sanitizer build flags.\n2. **Trigger:** minimized input / PoV / HTTP request sequence / SQL payload.\n3. **Oracle spec:** which oracle, expected verdict (e.g., \"ASAN heap-buffer-overflow at frame X\"), and — critically — the **random seed / challenge** used (§Diff-1) so re-verification issues a *fresh* challenge.\n4. **Solver witness (if used):** the SAT model for path feasibility.\n5. **Provenance envelope:** wrap all of the above in a **DSSE / in-toto attestation**, sign **keyless via Sigstore** (Fulcio cert → cosign → Rekor transparency-log inclusion). Now the certificate is tamper-evident, attributable, and independently verifiable.\n\n**Maturity:** Reproducer artifacts = **production** (OSS-Fuzz). Signed attestation wrapping = **production** (Sigstore/SLSA). Combining them into a *security-finding certificate* is **greenfield** — your opportunity.\n\n**Pipeline fit:** This is the output stage. A finding that can't be packaged into a re-runnable certificate should be downgraded to Abstain.\n\n---\n\n# The 3–5 DEEPEST, most differentiating techniques to build\n\nThese are the moves that make your findings *provably* trustworthy in a way current AI-hackers (XBOW, and most agentic pentest tools — which ultimately trust an LLM judgment plus a light \"validator\") do **not** do.
