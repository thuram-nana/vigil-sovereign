# W16-STD-2 — close the cloud/K8s + secret-discovery gaps (code parts)

Issue #528. Four code-side gaps closed to the government-deployment bar. The one part that is NOT code —
minting at least one LIVE cloud/K8s FACT against owned infrastructure — needs operator authorization and real
cloud credentials (the FACT checkpoint) and is called out as a residual below, not done here.

Each claim below is machine-checked by `docs/tests/test_claims_registry.py` (a claim marker, an enforcing
symbol, a proving test in a required CI job).

## (a) The `cross_account_principal` evidence branch is now cited by a real code path

The registered branch `cloud_live.cloud_posture.cross_account_principal` was cited by nothing: every
cloud_posture firing was filed under the generic `achieved_state` branch, and the branch's extra precondition
(`owner_account_supplied`) was evaluated nowhere. We chose to WIRE it (not remove it): the
`named_cross_account_principal` oracle rule genuinely fires, the branch describes a real distinct FACT-capable
capability with its own precondition and control-requirements, and the producer already returned the fired
`rules` set precisely for this per-rule attribution. Removing it would discard a real capability and its
honesty caveats; wiring is the sound option.

<!-- CLAIM:W16-STD-2a --> The registered `cloud_live.cloud_posture.cross_account_principal` evidence branch is cited by a real code path: `cloud_live_verify` attributes a cloud_posture firing whose fired rule is `named_cross_account_principal` to that branch and evaluates the branch's `owner_account_supplied` precondition over the retained control, instead of filing every cloud firing under the generic achieved_state branch; a wildcard/anonymous firing stays on achieved_state and a cross-account grant with no owner-account threaded in mints no cross-account FACT.

## (b) E5's secret-type recognition is broadened from two types to four

The E5 recognizer set (`oracles._SECRET_RECOGNIZERS`) recognised only `aws_access_key` and `github_pat`. It
now also recognises `gitlab_pat` and `slack_token`, each a sound FACT-capable row — a per-type
identity-confirming endpoint (GitLab `GET /api/v4/user`, Slack `auth.test`), a per-type anti-laundering host
allow-list, and a positive-evidence-only identity extractor. The runner's mirror table
(`secret_runner._SECRET_TYPES`) is kept in lock-step (a drift test pins them). Only the `github_pat` row is
live-fire proven; the other three are built and unit-proven, not live-fire proven.

<!-- CLAIM:W16-STD-2b --> The E5 exposed-secret recognizer set (`_SECRET_RECOGNIZERS`) covers four secret types — aws_access_key, github_pat, gitlab_pat, slack_token — each with its own per-type identity-confirming endpoint and anti-laundering host allow-list, and the deterministic oracle fires on a well-formed capture of any of them while a mutation of any single field (a wrong host, a cross-type action, an absent identity echo, a broken fingerprint binding) leaves it a LEAD.

## (c) A secret-DISCOVERY runner (LEAD, never FACT from tool bytes)

`live/secret_discovery.py` hunts a retained text surface for strings whose SHAPE matches a known secret format
and emits secret-safe CANDIDATES. The invariant: a candidate is a LEAD, never a FACT — the module has no
mint/admit/certify path. It recognises a SUPERSET of the oracle's FACT-capable types (a Google API key, a
Slack webhook URL are recognised as LEADs but honestly marked not-promotable). A candidate becomes a FACT
solely through the WARDEN-gated confirming call adjudicated by the E5 oracle; a candidate's bytes alone never
fire the oracle.

<!-- CLAIM:W16-STD-2c --> The exposed-secret DISCOVERY runner (`secret_discovery.scan`) finds secret candidates across a retained text surface and emits them as LEADs only — it exposes no code path that mints, admits, or certifies a FACT; a discovered candidate becomes a FACT solely through the WARDEN-gated confirming call adjudicated by the E5 oracle, so a candidate routed through the oracle with no confirming call never fires (it stays a LEAD), while benign text and near-miss shapes yield no candidates at all.

## (d) The evidence-tier sentence is generated from the registry, not hand-written

The one-line "of N registered oracle kinds, X external, Y own-infra, Z loopback, W fixtures-only" summary was
hand-written in OUTSTANDING.md and had drifted from the registry (it said "2 external ... ~14 loopback"; the
registry is 3 / 2 / 13 / 20). It is now GENERATED by `gen_coverage_tiers.py:render_sentence` from the same
registry-grounded counts as the coverage table, published between markers in OUTSTANDING.md, and a drift guard
asserts it matches the registry.

<!-- CLAIM:W16-STD-2d --> The one-line evidence-tier summary ("of N registered oracle kinds, X external, Y own-infra, Z loopback, W fixtures-only") is generated from the registry-grounded counts by `render_sentence` and published between markers in OUTSTANDING.md, and a drift guard fails the build if the published sentence does not match the per-tier counts derived from the OracleKind registry.

## RESIDUAL — the live cloud/K8s FACT checkpoint is NOT done

At least one LIVE cloud/K8s FACT against owned infrastructure is NOT minted here and is out of scope for the
code parts: it needs the operator's explicit authorization plus real cloud credentials (the FACT checkpoint).
Everything code-side is built and offline-proven with fixtures; the live run needs an operator-provisioned
read-only cloud/K8s credential in an authorized account. Nothing in this change claims a live cloud/K8s FACT
exists.
