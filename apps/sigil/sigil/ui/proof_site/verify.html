For auditors

Verify a VIGIL finding yourself.

Every finding VIGIL reports to a customer carries a cryptographic proof. If a VIGIL customer gave you a finding's proof bundle, you can check it here in three steps — offline, with no VIGIL account and none of VIGIL's software.

What you are checking

Two anchors, one of them yours to check

A VIGIL finding is a proof-carrying finding: VIGIL's oracle confirms the issue from evidence VIGIL captured itself, and the result is written into a signed evidence certificate — the finding's class, its location, a SHA-256 digest of the exact evidence the oracle judged, and a note on how to verify and fix it.

  1. Governance signature (in the bundle). VIGIL's governance keys sign that certificate; a threshold of distinct keys (m of n) must agree. This is what the proof bundle lets you check, byte for byte.
  2. Ledger anchor (on VIGIL's side). The signed certificate is then appended to the customer's tamper-evident ledger, chained under a head the owner key signs. VIGIL checks this anchor on its servers; it is not part of the download.

Step 1 — pin VIGIL's governance fingerprint

The proof bundle contains a copy of the governance trust root (public keys only). A copy can be swapped, so the check is anchored by a fingerprint you take from this page — not from the bundle:

__VIGIL_PROOF_PUBLISHED__

Step 2 — get the verifier and check it

The verifier is one small, auditable Python file. It imports only the Python standard library and the cryptography package — nothing of VIGIL's. The bundle includes a copy; you can also download it here. Either way, check its SHA-256:

sha256sum verify_pcf.py
__VIGIL_VERIFIER_SHA256__  verify_pcf.py

Step 3 — verify, offline

python3 -m pip install cryptography
unzip vigil-proof-*.zip -d proof && cd proof
python3 verify_pcf.py finding --bundle proof-bundle.json --trust-root-fingerprint <the fingerprint from step 1>

Exit code 0 and a last line of finding VERIFIED mean the proof checks out. Try the tamper test: change any value of the certificate in proof-bundle.json (its bug_class or surface, for example) and run it again — it prints finding NOT VERIFIED and exits 2. A file that is no longer valid JSON is an input error and exits 3.

What a verified result proves

That the certificate was signed by at least the threshold of distinct VIGIL governance keys behind the fingerprint you pinned, and that not one byte of it has changed since — its class, location, evidence digest and every other field. And that it declares a FACT provenance: it was minted from evidence VIGIL captured or re-drove itself, never from a model's text.

What it does not prove on its own

That the issue still reproduces today: re-running VIGIL's deterministic oracle needs the retained evidence and VIGIL's own verifier. It does not show that no other finding of the same assessment was withheld (that is the engagement chain, which a single-finding bundle does not carry). The verifier prints which checks it ran and which it did not.

The standard

The bundle follows VIGIL's published proof-carrying-finding wire format (PCF v0.1): canonical JSON, a domain-separated Ed25519 m-of-n threshold with weak-key rejection, and an out-of-band trust-root fingerprint. The verifier is derived from that specification, not from VIGIL's code, and it says exactly which layers it checked. Its bytes are pinned by VIGIL's signed verifier provenance — the SHA-256 shown in step 2.
